# M6-T2 — glTF export validated in Blender

BUILD_PLAN M6-T2: *"Validate export in Blender (materials intact, deck groups present, no flipped
normals)"*. PRD §13: *"the glTF interior loads in Blender with material slots intact and deck groups
named per contract."*

This is the machine-gate verdict for the M6-T1 export, checked against **two independent readers**:
the headless consumer model (`src/export/blender.ts`, run by the vitest suite) and **Blender's own
glTF importer** (`scripts/blender-validate.py`, run headless through the `bpy` module).

## Toolchain

- Blender **5.0.1** as a Python module (`pip install bpy` into a dedicated venv), imported headless
  (`bpy.ops.wm.read_factory_settings` → `bpy.ops.import_scene.gltf`). No display, no GUI.
- Corpus: the four canonical ships exported by the M6-T1 pipeline to `dist/export/<slug>.gltf`
  (JSON glTF, embedded buffer), regenerated by `npm run validate:export`.

```
npm run validate:export                                  # write dist/export/*.gltf + headless checks
BLENDER_PYTHON=/tmp/bpyenv/bin/python npm run validate:blender
```

Blender imports every file with no problems (`ok: true`). The deck groups import as the scene roots,

The headless model agrees exactly: `blenderValidation` is clean (no problems) on all four fixtures
and the `auditNormals` tally matches the Blender read (see `src/export/blender.test.ts`).

## Negative controls (the checks are not blind)

The validators were proven to *detect* drift, not just sign off:

- **Flipped normals** — negating every NORMAL accessor in `firebrand.gltf` makes both readers report
  the inversion: the headless audit flags the affected triangles and Blender reports
  **6,184/6,184 polygons flipped** (every face winding against its corner normals).
- **Deck group drift** — renaming `deck-3` to `cargo-bay-3` is reported by the headless
  `deckGroupCheck` and by Blender (its imported roots no longer match the file's scene order).
- **Malformed file** — a document whose primitive references a dropped material is refused by
  Blender's importer; `scripts/blender-validate.py` reports the refusal as a problem (never throws)
  and exits non-zero.

## Why two readers

The headless model (`src/export/blender.ts`) is the CI-checkable gate: it is deterministic, needs no
Blender, and runs in `npm test`. The `bpy` leg is the authoritative external consumer — it uses the
same importer a person opening the file in Blender would — and its verdict is recorded here. A file
that passes the headless gate but fails Blender would mean the model had drifted from the real
importer; pinning both on the same corpus closes that gap.
